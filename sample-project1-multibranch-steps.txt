*** Why Both(Multibranch or Pipeline) Can't Use the Same Push Events
Only one Jenkins job (Multibranch or Pipeline) can reliably respond to GitHub push events for a given repo.
This is because:GitHub sends the same webhook payload to Jenkins
Jenkins must decide which job to trigger
If both jobs are listening to the same webhook:
Only one (usually the multibranch one) will process it correctly
The other may not react or behave unpredictably

Study notes to understand the concept:
kops is stateless on your local machine
It doesn't save the cluster name or state bucket between sessions.

It fetches cluster configuration from the S3 bucket — not your local disk.

kops works with S3-based state storage
Every time you run a kops command (like get cluster, edit cluster, update cluster), it must know:

What your cluster name is (KOPS_CLUSTER_NAME)

Where to read/write the configuration (KOPS_STATE_STORE)

3. 🖥️ Environment variables are session-specific
When you run:
export KOPS_CLUSTER_NAME=test.k8s.local
export KOPS_STATE_STORE=s3://surya-k8-practice-bucket-2244

It sets these only for the current shell session.
If you close the terminal, those variables are gone.

How to Avoid Exporting Every Time:-
Add these exports to your shell config file so they are automatically set in every terminal session:

For Bash:
echo 'export KOPS_CLUSTER_NAME=test.k8s.local' >> ~/.bashrc
echo 'export KOPS_STATE_STORE=s3://surya-k8-practice-bucket-2244' >> ~/.bashrc
source ~/.bashrc

#### Assumption 3: Access to **kubeconfig**

Ensure that your Jenkins pipeline can access the Kubernetes cluster via the `kubeconfig` file. 

Kubeconfig : it is used by kubectl. jenkins should have it to connect kubernetes cluster so that it can apply kubectl commands on kubernetes cluster with proper info and authentication.
A kubeconfig file is a configuration file used by kubectl (and other Kubernetes clients) to connect to a Kubernetes cluster.

It contains details like:

The cluster API server endpoint

Authentication credentials (like certificates or tokens)

Namespaces

Context (which cluster/user/namespace to use by default)

The default location for this file is:
~/.kube/config

Jenkins itself doesn't "know" how to talk to Kubernetes directly. To deploy to Kubernetes from Jenkins, we:

Provide a kubeconfig file with access credentials to the target Kubernetes cluster.

Use this file so that kubectl knows where to connect and how to authenticate.

Without this file:
Jenkins (and kubectl) has no idea how to access your Kubernetes cluster.
